## 1. Application, dataset, and research questions

The application is a C++17 command-line movie catalog. Users can retrieve a movie by ID, find movies containing all selected genres, or search an inclusive average-rating range. Results include the title, genres, and average rating. Exact ID lookup is the primary operation because it retrieves one known record; genre and rating filters are secondary operations for browsing. The comparison asks whether changing storage improves these different search patterns.

The supplied MovieLens 1M files contain 3,883 movies, 6,040 users, and 1,000,209 ratings. Movie records contain an ID, title with release year, and pipe-separated genres. Ratings contain user ID, movie ID, whole-star rating from 1 to 5, and timestamp. User records contain demographic fields, but these fields are not search predicates. Movie IDs span 1-3952 with gaps, so a movie ID cannot safely be treated as a vector position. GroupLens provides the dataset [1, 2].

Research questions: (1) Is hash-table ID lookup faster than a sequential vector scan at three catalog sizes? (2) Does the same storage change help genre and rating filtering? (3) Can a researched composite-key treap provide a useful alternative? All implementations expose the same query interface, use cached arithmetic means, and return filter results in ascending movie-ID order. Unrated movies are excluded from rating filters.

## 2. Candidate structures and theoretical analysis

MovieDatabase owns vectors and scans its movie vector for an ID. MovieDatabaseMap owns unordered maps keyed by identifiers and uses hash lookup for IDs. Neither implementation maintains a genre index or an ordered rating index: both scan every movie and sort the matches. This corrects the proposal assumption that merely storing movies in a hash table would accelerate genre filtering.

| Operation | Vector | Hash table |
| --- | --- | --- |
| Movie ID lookup | O(n) worst case | Expected O(1); O(n) worst case |
| Genre filtering | O(n + k log k) | Expected O(n + k log k) |
| Rating filtering | Expected O(n + k log k) | Expected O(n + k log k) |
| Cached average lookup | Expected O(1) | Expected O(1) |

Here n is the movie count and k is the number of returned movies. Genre counts, query lengths, and identifier sizes are bounded for MovieLens 1M. Rating filtering uses a hash-based average cache in both versions; pathological collisions can increase its cost. The k log k term accounts for explicit output sorting. Returning k matches itself requires at least O(k) work. We predict a clear hash advantage for IDs, but no asymptotic filtering advantage. Contiguous vector storage may help scans; this is a hypothesis about constants, not a measured cache effect.

## 3. Experimental design and correctness checks

Three nested catalog sizes were generated by shuffling the source movie records once with Python random seed 20261020, taking the first n records, and sorting each subset by ID. Every rating for a selected movie was retained, preserving its full-data average. All 6,040 user records were retained. Fixtures were temporary; source data was not edited. The resulting sizes were 500 movies / 134,492 ratings, 2,000 / 508,928, and 3,883 / 1,000,209.

Each size used five fresh-process trials per implementation, rotating execution order. Each trial loaded the database, warmed each workload once, and then timed 100 repetitions with C++ steady_clock. Loading, average computation, tree construction, and fixture/query preparation were outside query timing. The build used Apple clang 17.0.0, C++17, -O2, -Wall, and -Wextra on an Apple M4 MacBook Air with 16 GB RAM running macOS 26.6.2. No link-time optimization was enabled.

ID lookup and cached-average lookup each queried every integer from 0 through 3953: 395,400 timed calls per trial. Genre filtering used the 18 canonical single genres plus Comedy/Romance and Action/Adventure/Sci-Fi: 2,000 calls. Rating filtering used [1,5], [1,2], [2,3], [3,4], [4,5], [3.5,4], and [5,5]: 700 calls. Filter timing includes result allocation, traversal for a checksum, and destruction, but excludes terminal output. Reported values are workload averages per call, then medians across five trials; they are not isolated instruction latencies.

The project built without new warnings and make test passed record-validation, round-trip, query, and treap-invariant checks. A separate untimed verifier compared movie records, exact optional averages, and complete ordered result-ID sequences across all three implementations for every benchmark query at every size. All comparisons passed. Benchmark checksums also agreed. CLI smoke checks exercised ID, genre, rating, invalid-menu input, exit, and EOF.

## 5. Interpretation and engineering recommendation

The hash table was fastest for ID lookup at every tested size. At 3,883 movies, its median was 1.65 ns/call, compared with 649.07 ns for the vector, approximately 393 times faster in this repeated workload. The vector time increased with catalog size, while hash lookup remained low. This agrees with the expected O(1) versus O(n) distinction, though three measurements do not prove asymptotic behavior.

Filtering produced a different result: the vector beat the hash-table version for both genre and rating workloads at all three sizes. Both scan all movies and sort matches, so the hash table has no indexing advantage for these predicates. Contiguous storage and cheaper traversal are plausible explanations, but cache misses and allocation behavior were not profiled. The result illustrates why a structure must match the operation, rather than simply be described as fast.

For an application dominated by exact ID requests, recommend a hash index. For the present small, mostly static catalog with frequent full filtering, vector storage remains a simple and competitive baseline. A practical extension is a vector owning the movies plus an ID-to-index hash table, giving direct lookup while retaining contiguous scans. That hybrid was not measured here. The CLI currently uses the vector database; these results support a future storage decision rather than claiming the interface already selects the fastest implementation.

## 6. Independent research: composite-key treap

A treap combines binary-search ordering on keys with heap ordering on random priorities. Rotations restore priority order after insertion. Random priorities yield expected logarithmic search paths; a degenerate tree can still have linear height [3]. Our optional implementation uses (movie ID, unrounded average rating, genre) as a lexicographic key, one node per movie/genre pair, with a fixed priority seed. Movies remain owned once in a vector.

With m movie/genre nodes, ID search takes expected O(log m), worst-case O(m). Subtree genre masks and minimum/maximum averages allow pruning; in-order traversal returns unique matches in ID order. These filters remain O(m) worst case. A leading movie-ID key does not independently order every genre or rating, correcting the proposal claim that all searches would average O(log n).

The treap had the fastest genre-filter medians at all sizes. It also had the fastest rating-filter median at every tested size. Its masks, pruning, and ordered traversal avoid some scanning and sorting work, at the cost of more nodes, metadata, and implementation complexity. These timings do not isolate the contribution of each optimization; the treap is useful research evidence, rather than a universal replacement.

## 7. Limitations, learning, and AI assistance

The fixed ID range yields 500, 2,000, and 3,883 hits per 3,954 queries, respectively. Changing hit rates confound pure size scaling; sequential warmed queries also differ from random or popularity-weighted traffic. Only one nested sample, machine, and fixed treap seed were tested. Filters have different output sizes and include checksum overhead. No memory, cold-cache, insertion/deletion, or per-query latency distributions were measured. Future work should fix hit ratios and profile memory before generalizing.

The main lesson is that direct-key retrieval and multi-result filtering require different indexes and tradeoffs. AI assistance through Codex was used to inspect code, prepare benchmark fixtures and verification tooling, collect measurements, research references, and draft and format this report. All reported timings were actually collected, and automated checks passed. Team review and the ability of each member to explain the design and results remain necessary before submission.
